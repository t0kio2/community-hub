# テナント管理プロトタイプ UI 設計

## 目的と背景

現行の `prototype/` は宿泊施設管理に特化しており、テナントが扱う求人と組織情報への導線がない。テナント管理者がログイン後に事業全体を把握し、宿泊・求人・組織設定へ迷わず移動できる共通 UI を整備する。

## 対象範囲

- テナント全体のホーム（宿泊、求人、応募対応のサマリー）
- 求人一覧、求人の公開状態切り替え、応募者一覧と選考状態の更新
- テナント基本情報、連絡先、公開プロフィールの編集
- 宿泊施設単位の既存画面を、新しいテナント共通ナビゲーションへ統合
- 既存 JSON と `localStorage` の後方互換

Rails API、DB、認証、求人の新規作成フォーム、メンバー招待と権限変更は今回の対象外とする。

## 影響ファイル

- `prototype/tenant.html`: テナント共通のサイドバーとヘッダー
- `prototype/styles.css`: 共通シェル、ホーム、求人、設定画面のスタイル
- `prototype/app.js`: 画面遷移、描画、入力・状態更新
- `prototype/domain.js`: ワークスペース初期化とテナントサマリー算出
- `prototype/data/stay-listing.json`: 求人、応募、テナントプロフィールのサンプル
- `prototype/tests/domain.test.mjs`: 後方互換とサマリー算出のテスト
- `prototype/README.md`: 追加画面と操作の説明

## データ方針

既存のテナント集約 JSON に `jobListings[]`、`jobApplications[]`、`tenant.profile` を追加する。認証・所属データはER図に合わせて `accounts[]` と `tenantMembers[]` に分離し、`currentAccountId` でログイン中のAccountを示す。旧データは `normalizeWorkspace` で既定のownerアカウントと有効なTenantMemberを補い、読み込みを継続できるようにする。編集結果は従来どおりブラウザの `localStorage` のみに保存する。

## 実装手順

1. ナビゲーションを「テナント」「宿泊管理」「求人管理」「組織設定」に再編する。
2. ホームに横断サマリー、対応が必要な項目、各機能への導線を表示する。
3. 求人一覧と応募者一覧を追加し、公開状態・選考状態を操作可能にする。
4. テナント情報編集とメンバー一覧を追加する。
5. 現在の画面コンテキストに応じてヘッダー操作と施設コンテキスト表示を切り替える。
6. 狭い画面でも確認できるレスポンシブ表示を追加する。

### サイドナビゲーションの区分

ホームはテナント全体の入口として独立させ、その下を「宿泊」「求人」「組織」の3グループに分ける。各グループはアイコン、名称、短い目的説明を持つカード状の領域とし、項目間の余白だけに依存せず境界を明示する。現在表示中の画面が属するグループにはアクセントを表示する。

宿泊グループ内の施設名はナビゲーション項目ではなく、現在の操作対象を表すコンテキストとして表示する。「管理中の施設」というラベルを「対象施設」へ簡潔化し、施設切り替えは「宿泊施設」画面から行う。

### ログインユーザー表示

サイドバー下部へログイン中のテナントアカウントを常時表示する。メールアドレス、テナント内の役割と在籍状態を一まとまりにし、テナントや対象施設の表示と混同しない配置にする。ユーザー領域からメンバー画面へ移動できるようにし、アカウント管理への入口として扱う。

ユーザー領域の遷移はコンテンツ領域の JavaScript イベント委譲へ依存させず、`href="#members"` を持つリンクとして実装する。JavaScript実行前やイベント監視範囲の変更後も遷移可能な構造を維持する。

画面の高さが低い場合もアカウント領域を画面外へ押し出さない。ブランドとアカウント領域を固定し、その間にあるナビゲーションだけを縦スクロールさせる。表示情報はownerアカウントであること、役割・状態、メールアドレスとする。

ER図上、テナント認証主体に氏名プロフィールはなく、`current_tenant_account -> tenant_member -> tenant` の関連で認証後のコンテキストを取得する。プロトタイプも `currentAccountId -> accounts[] -> tenantMembers[] -> tenant` とし、ログイン中のAccountは `account_type = tenant`、所属は `role = owner`、`status = active` とする。認証処理とログアウト処理自体は対象外とする。

## 検証とテスト

- 旧形式データに追加フィールドがなくても正規化できること。
- 認証・所属データがない旧データでは有効なownerアカウントとTenantMemberが補完されること。
- 公開求人、対応待ち応募、公開施設の件数がテナント横断で正しく集計されること。
- 求人・応募データがない場合も 0 件として扱うこと。
- Node.js 標準テストを実行し、既存の宿泊ドメインテストも回帰確認する。
- 静的 HTTP サーバーで主要画面と画面遷移を確認する。

## トレードオフと今後

UI 検証を優先し、求人の入力項目と選考状態は最小構成にする。正式実装時は求人ドメインの API 契約、権限別ナビゲーション、監査履歴、下書き保存、バリデーションを別途定義する。
