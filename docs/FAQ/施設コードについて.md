
› IDがURLに出ているのは良くないよね？institute_codeのような番号があったほうがいいね


• DBの連番IDがURLに出ること自体は、セキュリティ上の問題ではありません。ただし、推測可能なIDを外部識別子として使い続けるより、宿泊施設コードを持たせる設計はよいと思います。

  名前はinstitute_codeより、意味が明確な以下がおすすめです。

  facility_code

  または宿泊施設に限定するなら、

  stay_code

  URL例：

  /tenant/stays/STY-8K2M4P
  /tenant/stays/STY-8K2M4P/rooms
  /tenant/stays/STY-8K2M4P/inventory
  /tenant/stays/STY-8K2M4P/rates

  設計としては、DB内部の関連付けには今までどおりlisting_idを使い、URLや画面上ではfacility_codeを使います。

  id
  └── DB内部の主キー・外部キー

  facility_code
  └── URL・画面・問い合わせで使う公開識別子

  stay_listingsではなく、宿泊施設の主体であるlistingsに持たせるかは注意が必要です。求人Listingには不要なので、このコードが宿泊施設固有ならstay_listingsに置くのが自然です。

  add_column :stay_listings, :facility_code, :string, null: false
  add_index :stay_listings, :facility_code, unique: true

  ただし、テナントごとにコードが重複してもよいなら複合ユニーク制約が必要です。tenant_idがlistingsにある現在の構造では、単純なDB制約が作りにくいため、公開コードは全体で一意にするのが扱いやすいです。

  コードは連番ではなく、推測しにくいランダム値にします。

  STY-8K2M4P
  STY-Q7X9DN

  Railsでは検索を次のようにします。

  @listing = @tenant.listings
                    .stay
                    .joins(:stay_listing)
                    .find_by!(stay_listings: {
                      facility_code: params[:id]
                    })

  またはルートのパラメータ名を明示すると分かりやすくなります。

  resources :stays, param: :facility_code

  params[:facility_code]

  URLからIDを隠しても認可の代わりにはなりません。必ず@tenant.listingsから検索し、別テナントの施設コードを入力しても取得できないようにする必要があります。

  なお、単に連番IDを隠したいだけならUUIDやULIDも選択肢ですが、施設コードは電話や問い合わせでも使えるため、短いランダムなfacility_codeの方が業務上は便利です。
