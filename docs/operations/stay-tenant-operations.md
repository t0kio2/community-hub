# テナントの宿泊関連業務

## 目的

宿泊施設を運営するテナントが、システム上で行う設定と基本業務を定義する。宿泊関連機能の設計、実装、テストおよび業務画面を検討する際の正本とする。

- 施設・販売設定: [`architecture/02-listing-stay.md`](../architecture/02-listing-stay.md)
- 予約管理: [`architecture/04-stay-reservation.md`](../architecture/04-stay-reservation.md)

## 対象範囲

宿泊業務は、大きく次の2領域に分かれる。

| 領域 | 目的 | CommunityHubの初期対象 |
| --- | --- | :---: |
| 販売管理 | 施設、Room Type、料金、在庫を公開し、予約を受け付けて管理する | ○ |
| ホテル運営（PMS） | チェックイン、滞在中対応、精算、清掃など現地運営を管理する | × |

初期仕様は販売管理を対象とする。物理Room・Bedは販売在庫の根拠と予約の割り当てに使用するが、清掃、カードキー、現地精算などのPMS機能までは扱わない。

## 業務の全体像

```text
① 施設・客室を登録する
        ↓
② 販売条件を設定する
        ↓
③ 販売を開始して予約を受ける
        ↓
④ 予約を確認し、部屋を割り当てる
        ↓
⑤ チェックイン準備
-------- 初期対象の境界 --------
⑥ チェックイン
        ↓
⑦ 滞在中管理
        ↓
⑧ チェックアウト
        ↓
⑨ 清掃・次の販売
```

⑤までをCommunityHubの初期対象とする。⑥以降は将来PMS領域へ拡張する場合に定義する。

# テナントによる設定

## 1. 施設を登録する

1つのStay Listingを、テナントが運営する1つの宿泊施設として登録する。

| 設定 | 主な内容 | 対応するモデル |
| --- | --- | --- |
| 施設基本情報 | 施設名、紹介文、画像 | `Listing / ListingImage` |
| 所在地 | 郵便番号、住所、座標、Place ID | `ListingLocation` |
| 宿泊設定 | チェックイン・アウト、ハウスルール、タイムゾーン | `StayListing` |
| 予約受付設定 | 即時確定または承認制、承認期限、宿泊可能期間、予約受付期間 | `StayListing` |
| 施設設備 | 共通Amenityの選択、テナント固有Amenityの追加 | `StayAmenity / StayListingAmenity` |

下書き保存では未完成を許可する。販売開始時は公開条件を一括確認し、不足項目と対応する設定画面を示す。

## 2. Room Typeを登録する

一般ユーザーが選択する販売上の客室分類を、施設ごとに作成する。

```text
スタンダードツイン
女性専用ドミトリー
一棟貸しコテージ
```

| 設定 | 内容 |
| --- | --- |
| 名称・説明 | 利用者向けのRoom Type情報 |
| 販売形態 | `entire_place / private_room / shared_room` |
| 定員 | Room単位の最大人数。相部屋はBed単位で1人 |
| 画像 | 客室内、寝具、客室内設備などRoom Typeを説明する販売用画像 |
| Amenities | Room Type単位の利用者向け設備 |
| 公開状態 | `draft / published / inactive` |

Room Typeを公開するには画像を1件以上登録する。物理Roomごとの公開画像は持たず、画像で示す必要がある差がある場合は別のRoom Typeへ分ける。部屋の広さと利用者向けベッド構成は現在未定義とする。

## 3. 物理Room・Bedを登録する

Room Typeに属する実際の客室を登録し、販売可能な物理在庫の根拠とする。

```text
スタンダードツイン
├─ 201号室
├─ 202号室
└─ 203号室

女性専用ドミトリー
└─ 301号室
   ├─ Bed A
   ├─ Bed B
   └─ Bed C
```

- 一棟貸し・個室は有効なRoom数を基本在庫とする。
- 相部屋は有効なRoomに属する有効なBed数を基本在庫とする。
- 恒久的な休止は`active = false`とする。
- 修繕や施設都合による一時停止はRoom・Bedの停止期間として登録する。

## 4. Rate Planと基本料金を登録する

Rate Planは、食事とキャンセル条件をまとめた施設固有の販売条件とする。

```text
素泊まり・キャンセル可
朝食付き・キャンセル可
素泊まり・返金不可
```

金額はRate Plan単体ではなく、Room TypeとRate Planの組み合わせごとに設定する。

```text
朝食付き・キャンセル可
├─ スタンダードツイン  15,000円
├─ デラックスツイン    20,000円
└─ 和室                  18,000円
```

異なるRate Planを販売しても、同じRoom Typeの物理在庫を共通で消費する。

## 5. 日別料金と販売上限を設定する

繁忙日、曜日、スタッフ数、他販売経路との調整に応じて日付ごとの例外を設定する。

| 設定 | 単位 | 未設定時 |
| --- | --- | --- |
| 日別料金 | Room Type × Rate Plan × 宿泊日 | 基本料金へ戻る |
| 日別販売上限 | Room Type × 宿泊日 | 物理在庫数まで販売する |
| 販売停止 | 日別販売上限を0にする | 販売を再開する場合は制御を削除する |

期間と曜日を指定した一括操作を提供する場合も、ルール自体は保存せず、対象日ごとの最終値を作成・更新する。

## 6. 販売を開始・停止する

次の順に公開状態を整える。

1. 有効な物理在庫を持つRoom Typeを`published`にする。
2. Rate Planを`published`にする。
3. Room TypeとRate Planに有効な基本料金を設定する。
4. Stay Listingの共通・固有公開条件を確認する。
5. Listingを`published`にして販売を開始する。

一時的な受付終了はListingを`closed`、廃止は`archived`とする。Room TypeとRate Planは必要に応じて`inactive`へ変更する。

# テナントの基本業務

## 7. ダッシュボードを確認する

ログイン後に、対応が必要な業務と施設全体の販売状況を確認する。

- 承認待ち予約と承認期限
- 今日・明日のチェックイン予定
- 今日のチェックアウト予定
- 販売停止、残在庫不足、販売上限超過の警告
- 未処理のキャンセルや問い合わせ

初期仕様で処理を持たない業務は、件数や案内だけを表示し、実行可能な操作と混同させない。

## 8. 販売カレンダーを確認・更新する

販売カレンダーをテナントの販売管理における中心画面とする。日付を横軸、Room Typeを縦軸にし、複数日の販売状態を比較できるようにする。

```text
                 8/1        8/2        8/3
スタンダード    残3        残2        停止
デラックス      残1        残1        残2
ドミトリー      残4        残2        残3
```

### Room Type・日付ごとの表示

- 物理在庫数
- Room・Bedの停止数
- 承認待ち予約の使用数
- 確定予約の使用数
- 日別販売上限
- 算出された残在庫
- 販売中・残りわずか・売切・販売停止・上限超過の状態

### 料金表示

選択したRoom Typeまたはセルの詳細で、Rate Planごとの基本料金と日別料金を表示する。Rate Planごとに在庫行を分けない。

### 主な操作

- 1日分の料金・販売上限を変更する。
- 期間と曜日を指定して料金・販売上限を一括変更する。
- 日別料金を削除して基本料金へ戻す。
- 日別販売制御を削除して物理在庫上限へ戻す。
- Room・Bedの停止期間を確認・登録する。
- 対象日の予約一覧へ移動する。

販売上限を既存の承認待ち・確定予約数より小さくした場合は、既存予約を維持したまま超過を警告し、新規予約可能数を0とする。

## 9. 予約申請を承認・拒否する

### 承認制

1. `requested`の新着申請を確認する。
2. 宿泊日、Room Type、Rate Plan、数量、人数、料金、代表宿泊者、メッセージ、承認期限を確認する。
3. 承認して`confirmed`にするか、拒否して`rejected`にする。
4. `expired`となった申請の仮確保在庫が解放されたことを確認する。

### 即時確定

1. `confirmed`で作成された新着予約を確認する。
2. 自動割り当てされたRoomまたはBedを確認する。

拒否理由、処理担当者および状態変更履歴の保存方法は未定義であり、予約操作を実装する前に決める。

## 10. 予約一覧と予約詳細を確認する

予約一覧では、少なくとも次の絞り込みを提供する。

- 今日・明日のチェックイン
- 今日のチェックアウト
- 承認待ち、確定、拒否、キャンセル、期限切れ、完了
- 宿泊日
- Room Type
- 代表宿泊者
- 予約番号

予約詳細では、現在の販売設定ではなく、予約時に固定した料金・キャンセル条件のスナップショット、宿泊者、メッセージ、物理在庫の割り当てを表示する。利用者へ案内する予約番号の形式は未定義とする。

## 11. Room・Bedの割り当てを調整する

予約受付時にシステムが自動割り当てしたRoomまたはBedを確認する。必要な場合は、同じRoom Typeに属し、予約期間全体で空いているRoomまたはBedへ変更する。

別Room Typeへの変更は単純な部屋割りではなく予約内容変更として扱う。日程、数量、人数、Room Type、Rate Planを変更する業務と再見積もりルールは未定義である。

## 12. キャンセルと販売停止に対応する

- 利用者のキャンセルでは、予約時のキャンセル条件からキャンセル料を算出し、在庫を解放する。
- `requested`中の利用者取消とテナント都合の取消は無料とする。
- テナント都合の取消理由、利用者への通知、返金処理は未定義とする。
- 故障などで特定Room・Bedを停止する場合、重複する既存予約を警告し、必要に応じて先に割り当てを変更する。

決済を扱わない段階ではキャンセル料を表示・記録する範囲とし、実際の請求・返金処理は対象外とする。

## 13. 施設・販売内容を保守する

- 施設情報、画像、住所、Amenityを更新する。
- Room Type、物理Room・Bed、Rate Planを追加・変更・停止する。
- 基本料金と将来の日別料金・販売上限を調整する。
- Listingの受付終了、再公開、アーカイブを行う。
- 無効化・アーカイブ後も過去予約とスナップショットを参照する。

公開中の設定変更は既存予約へ遡及させず、新規予約だけへ適用する。影響する予約がある変更では、保存前に対象件数と非遡及を警告する。

# 将来のホテル運営業務（PMS）

## 14. チェックイン準備

販売管理の範囲では、今日・明日のチェックイン予定、代表宿泊者、人数、滞在日数、部屋割りを確認できるところまでとする。

## 15. 初期対象外の業務

次の業務は実際の宿泊運営には必要だが、CommunityHubの初期仕様には含めない。

- チェックイン日時と担当者の記録
- 本人確認と法令上の宿泊者名簿
- カードキー発行
- 現地支払いと精算
- 滞在中の延泊、追加料金、備品対応
- チェックアウト日時と担当者の記録
- 領収書発行
- 清掃待ち、清掃中、点検済み、販売可能などの客室状態
- 無断不泊の業務処理
- 売上、稼働率、キャンセル率などの集計
- 会計、清掃、外部販売チャネルとの連携

予約を`completed`へ遷移する条件と、無断不泊を予約状態として扱うかは、PMS領域へ拡張しなくても予約ライフサイクルを完結させるため、別途定義する。

## 現在の未決事項

販売管理の実装前に、少なくとも次を決める。

1. 予約番号の形式と検索仕様
2. 承認・拒否・取消の理由、担当者、状態変更履歴
3. 予約内容変更の可否と再見積もり・在庫再確保
4. テナント都合取消と通知
5. 同行者情報を変更できる期限
6. `completed`と無断不泊の状態遷移
7. Room Typeの広さと利用者向けベッド構成の要否
