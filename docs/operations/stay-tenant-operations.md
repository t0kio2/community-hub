# テナントの宿泊関連業務

## 目的

宿泊施設を運営するテナントが、システム上で行う業務、操作の目的、現在の仕様化状況を定義する。宿泊関連機能の設計、実装、テストおよび業務画面を検討する際の正本とする。

- 施設・販売設定: [`architecture/02-listing-stay.md`](../architecture/02-listing-stay.md)
- 予約管理: [`architecture/04-stay-reservation.md`](../architecture/04-stay-reservation.md)

## 業務の全体像

```text
導入・販売準備
  ↓
日々の販売調整 ──────┐
  ↓                  │
予約申請・予約確定     │
  ↓                  │
来訪前の予約管理       │
  ↓                  │
チェックイン・滞在対応 │
  ↓                  │
チェックアウト・完了 ─┘

随時: 施設情報、料金、在庫、休室、問い合わせ、キャンセル対応
```

## 1. 導入・販売準備

施設の販売を開始するまでに行う初期設定である。施設開設時だけでなく、改装や販売形態変更時にも行う。

| 業務 | 主な操作 | 現在の設計 |
| --- | --- | --- |
| 施設情報を登録する | 施設名、説明、画像、住所、座標、ハウスルールを入力 | 定義済み |
| 予約受付条件を決める | 即時確定または承認制、承認期限、チェックイン・アウト、受付期間を設定 | 定義済み |
| 施設設備を設定する | 共通Amenityを選択し、必要ならテナント固有Amenityを作成 | 定義済み |
| Room Typeを作る | 名称、説明、一棟・個室・相部屋、定員、Amenityを設定 | 定義済み |
| 物理在庫を登録する | Roomを登録し、相部屋の場合はRoomにBedを登録 | 定義済み |
| Rate Planを作る | 食事条件、標準または返金不可のキャンセル条件を設定 | 定義済み |
| 基本料金を設定する | Room TypeとRate Planの組み合わせごとに1泊料金を設定 | 定義済み |
| 公開前確認をする | 共通・Stay固有の公開条件を確認し、Room Type、Rate Plan、Listingを公開 | 定義済み |

公開操作では「設定項目を順に入力する」だけでなく、どの設定が公開を妨げているかを施設全体から確認できる必要がある。

## 2. 日々の販売・在庫調整

予約受付状況、スタッフ数、修繕、清掃、繁忙日などに応じて販売可能数と料金を調整する業務である。

| 業務 | 主な操作 | 現在の設計 |
| --- | --- | --- |
| 日別料金を調整する | Room Type・Rate Plan・日付ごとの料金を設定、削除して基本料金へ戻す | 定義済み |
| 日別販売上限を調整する | Room Type・日付ごとの販売上限を設定。0で販売停止 | 定義済み |
| 期間・曜日で一括設定する | 画面で期間・曜日を指定し、対象日レコードを一括更新 | 方針定義済み |
| Room・Bedを一時停止する | 修繕、清掃、施設都合の停止期間を登録 | 定義済み |
| Room・Bedを長期休止する | `active = false`に変更 | 定義済み |
| 販売超過を確認する | 既存予約数を下回る販売上限を設定した場合の警告を確認 | 定義済み |
| 日別の残在庫を確認する | 物理空き数と販売上限残数の小さい方を表示 | 定義済み |

日常業務では個別の設定画面だけでなく、日付を横軸、Room Typeを縦軸にした販売カレンダーが中心画面になる。料金、上限、予約済み数、停止数、残数を同じ日付単位で比較できることが重要である。

## 3. 予約申請・予約確定

利用者から届いた予約を確認し、在庫を確定する業務である。

### 承認制

1. `requested`の新着予約申請を確認する。
2. 宿泊日、Room Type、Rate Plan、人数、金額、代表宿泊者、メッセージ、承認期限を確認する。
3. 承認して`confirmed`にするか、理由を確認して`rejected`にする。
4. 承認期限切れの申請は`expired`となり、仮確保された在庫が解放されたことを確認する。

### 即時確定

1. `confirmed`の新着予約を確認する。
2. 自動割り当てされたRoomまたはBedと、宿泊者情報を確認する。
3. 必要なら同じRoom Type内の空きRoomまたはBedへ割り当てを変更する。

承認・拒否、期限切れ、即時確定、自動割り当て、同一Room Type内の割り当て変更は定義済みである。拒否理由を保存・通知する方法と、担当者別の処理履歴は未定義である。

## 4. 来訪前の予約管理

予約確定後からチェックインまでに行う準備業務である。

| 業務 | 主な操作 | 現在の設計 |
| --- | --- | --- |
| 予約を検索する | 宿泊日、状態、予約番号、代表宿泊者で検索 | UI・検索条件は未定義 |
| 予約詳細を確認する | 料金・キャンセル条件のスナップショット、連絡先、メッセージを表示 | データは定義済み |
| 同行者を更新する | チェックインまで同行者の追加・変更・削除 | 概要定義済み、期限未確定 |
| 部屋割りを調整する | 同一Room Typeの空きRoom・Bedへ変更 | 定義済み |
| 予約内容を変更する | 日程、数量、人数、Room Type、Rate Planを変更 | 未定義 |
| 利用者キャンセルを処理する | スナップショットからキャンセル料を算出し、在庫を解放 | 算出方針は定義済み、返金処理は未定義 |
| テナント都合で取消する | 予約を取消し、利用者へ連絡して在庫を解放 | 状態・通知・返金ルールは未定義 |

予約内容変更は料金の再見積もり、旧在庫の解放、新在庫の確保を同時に扱うため、実装前に業務ルールを確定する必要がある。

## 5. 当日の宿泊運営

当日の到着、滞在、出発を管理する業務である。実際の宿泊運営には必要だが、現在の予約設計では十分に定義されていない。

| 業務 | 想定する操作 | 現在の設計 |
| --- | --- | --- |
| 本日の到着を確認する | チェックイン予定、部屋割り、人数、連絡先を一覧表示 | 未定義 |
| チェックインを記録する | 到着日時と担当者を記録 | 未定義 |
| 未到着を扱う | 遅延連絡または無断不泊として記録 | 無断不泊の料金のみ定義、状態未定義 |
| 滞在中の部屋を変更する | 故障などによる物理Room変更を記録 | 同一Room Type内の変更のみ概ね定義済み |
| チェックアウトを記録する | 出発日時と担当者を記録 | 未定義 |
| 宿泊を完了する | 予約を`completed`へ遷移 | 状態値のみ定義、遷移条件は未定義 |

この領域は、予約状態だけで運営するか、チェックイン・アウトを別の業務イベントとして記録するかを今後決める。

## 6. 施設・販売内容の保守

| 業務 | 主な操作 | 現在の設計 |
| --- | --- | --- |
| 施設情報を更新する | 公開条件を維持しながら説明、画像、住所などを変更 | 定義済み |
| Room Typeを停止・再公開する | `inactive / published`を切り替える | 定義済み |
| Rate Planを停止・再公開する | `inactive / published`を切り替える | 定義済み |
| 施設の受付を終了・再開する | Listingを`closed / published`へ遷移 | 定義済み |
| 施設を保管する | Listingを`archived`へ遷移 | 定義済み |
| 過去予約を参照する | 無効化・アーカイブ後もスナップショットを表示 | 定義済み |

公開中の設定変更は既存予約へ遡及させず、新規予約だけへ適用する。影響する既存予約がある変更では、保存前に件数と非遡及を警告する必要がある。

## 7. 問い合わせ・通知・集計

宿泊運営では必要になるが、Listing・予約の現在の設計範囲外または未定義である。

- 予約前の施設への問い合わせ
- 予約申請、承認、拒否、期限切れ、キャンセルの通知
- 宿泊前の案内メッセージ
- テナント内の未処理タスクと担当者
- 売上、稼働率、キャンセル率などの集計
- CSV出力、会計・清掃システムとの連携

初期仕様では実処理を作らず、ダッシュボード上の「未処理件数」や通知例として必要性と優先順位を確認する。
