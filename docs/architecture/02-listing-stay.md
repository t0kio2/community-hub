# 滞在Listing定義

## 目的

滞在Listingにおける施設、部屋、物理在庫、料金プランおよび予約受付設定の責務を定義する。個別予約の受付、状態遷移、物理在庫の割り当て、宿泊者、料金・キャンセル条件のスナップショットは [`04-stay-reservation.md`](./04-stay-reservation.md) を参照する。

テーブル構造は [`../er/01-listing-stay.md`](../er/01-listing-stay.md) を正本とする。Listing共通仕様は [`02-listing.md`](./02-listing.md)、住所・位置情報は [`03-location.md`](./03-location.md) を参照する。

## 宿泊施設・部屋・在庫の単位

1つのListingは、テナントが運営する1つの宿泊施設を表す。施設は1つ以上のRoom Typeを持ち、一般ユーザーは物理的な部屋ではなくRoom Typeを選択する。

Room Typeはシステム共通マスターではなく、テナントが自ら所有する宿泊施設ごとに作成する販売上の部屋分類とする。同じ名称でも施設が異なれば別のRoom Typeとして扱う。テナントは自ら所有する施設にのみRoom Typeを作成・更新できる。

物理的な宿泊空間はRoomとして登録し、同じ施設に属する1つのRoom Typeへ紐づける。一般ユーザーにはRoomを選択させない。

```text
Tenant
└─ Listing（宿泊施設）
   └─ StayListing（施設共通の宿泊情報）
      ├─ RoomType（販売上の部屋分類）
      │  └─ Room（物理的な部屋）
      │     └─ Bed（相部屋内の物理的なベッド）
      └─ RatePlan（食事・キャンセル等の販売条件）
```

| `room_kind` | 販売形態 | 販売・在庫の単位 |
| --- | --- | --- |
| `entire_place` | 一棟または独立した空間を貸し切る | Room |
| `private_room` | 施設内の個室を貸し切る | Room |
| `shared_room` | 他の宿泊者と共有する相部屋 | Bed |

1つのRoom TypeでRoom単位とBed単位の販売を混在させない。物理在庫を登録するため、Room Typeに手入力の在庫数は持たない。`entire_place / private_room`の基本在庫は有効なRoom数、`shared_room`は有効なBed数から算出する。一棟貸しは一棟を表すRoomを1件登録する。

## 物理在庫の停止

施設都合による一時停止は、RoomまたはBedと停止期間を紐づけて管理する。`active`は恒久的な有効・無効に使用し、修繕、清掃、手動停止など日付を伴う停止には使用しない。

停止期間はチェックイン日を含みチェックアウト日を含まない半開区間として扱う。同じRoomまたはBedの停止期間同士は重複を許可するが、予約へ割り当て済みの期間と重複する停止は作成できない。

## Room Typeの日別販売制御

人員不足、団体向けの在庫確保、他販売経路との調整など営業上の理由で物理在庫数より少なく販売する場合は、`stay_room_type_daily_sales_controls`でRoom Typeと宿泊日ごとの販売上限を管理する。Rate Planによって物理在庫は増減しないため、Rate Planには紐づけない。

`sales_limit`はその宿泊日に販売できるRoomまたはBedの総数であり、予約の`quantity`と同じ単位とする。

| 状態 | 意味 |
| --- | --- |
| 日別販売制御レコードなし | 物理在庫数まで販売可能 |
| `sales_limit > 0` | 指定数を販売総数の上限とする |
| `sales_limit = 0` | その宿泊日のRoom Typeを販売停止する |

販売停止用のbooleanは持たない。日別販売制御を削除すると販売制限を解除し、物理在庫数まで販売可能な状態へ戻す。

日別販売制御は物理Room・Bedの状態を変更しない。特定の物理在庫を一時停止する場合は`stay_room_blocks / stay_bed_blocks`、廃止・長期休止する場合は`active = false`を使用する。

テナントは期間、曜日、販売上限を指定して一括設定できる。期間ルール自体は保存せず、日別料金と同様に対象日ごとのレコードを作成または更新する。

既存の`requested / confirmed`予約数より小さい上限への変更を許可するが、超過数と既存予約が維持されることを警告する。上限超過中の新規予約可能数は0とする。販売上限が物理在庫数より大きい設定も許可するが、実際の予約可能数は物理空き数を超えない。

## Room Typeの定員

Room Typeの`capacity`は、1つの販売在庫単位へ宿泊できる最大人数を表す。公開するRoom Typeでは必須かつ1以上とする。

| `room_kind` | 1販売在庫単位 | `capacity` |
| --- | --- | --- |
| `entire_place / private_room` | Room | 1 Roomあたりの最大宿泊人数 |
| `shared_room` | Bed | 1固定 |

相部屋の物理Room全体の収容人数は、そのRoomに属する有効なBed数から算出し、Room Typeの`capacity`には持たない。予約人数の検証は予約仕様で定義する。

## Amenities

Amenitiesは自由入力テキストではなく、`stay_amenities`マスターと関連テーブルで管理する。初期データセットはシステムが提供し、テナントは共通Amenitiesの選択に加えて自テナント固有Amenitiesを作成できる。

`stay_amenities.tenant_id = NULL`はシステム共通、テナントIDありはそのテナントだけが使用できる固有Amenitiesを表す。

| 操作 | テナント | システム運営 |
| --- | :---: | :---: |
| 共通Amenitiesの選択 | ○ | ○ |
| 共通Amenitiesの作成・変更・無効化 | × | ○ |
| 自テナント固有Amenitiesの作成・変更・無効化 | ○ | ○ |
| 他テナント固有Amenitiesの選択・変更 | × | ○ |

Amenitiesは設定可能な対象を`scope`で制限する。

| `scope` | 設定可能な対象 |
| --- | --- |
| `facility` | `stay_listing_amenities`による施設全体 |
| `room_type` | `stay_room_type_amenities`によるRoom Type |
| `both` | 施設全体とRoom Typeの両方 |

カテゴリは`connectivity / climate / bathroom / kitchen / bedding / accessibility / safety / parking / service / other`とする。`code`は検索とAPIで使用する変更不可の識別子、`name`は利用者向け表示名とする。テナント固有Amenitiesの`code`はシステムがテナント名前空間で生成し、テナントには入力・変更させない。共通コードとの衝突を許可しない。

共通Amenitiesは全テナント横断の検索条件に使用できる。テナント固有Amenitiesは施設・Room Typeの詳細表示に使用するが、初期仕様では横断検索条件にしない。複数のRoom Type Amenitiesを指定した検索では、同じ`published` Room Typeがすべての条件を満たさなければならず、別々のRoom Typeに条件を分散して満たしてはならない。

同じRoom Typeに属する物理Roomは利用者向けAmenitiesが同じである前提とする。設備が大きく異なる物理Roomは別のRoom Typeへ分け、物理Room単位のAmenitiesは初期仕様では持たない。

AmenitiesはListingおよびRoom Typeの公開必須条件にしない。`active = false`のAmenitiesは新しい関連付けと現在の公開表示・検索から除外するが、既存の関連レコードは保持する。関連が存在するAmenitiesは物理削除せず無効化する。`scope`は関連作成後に変更できない。

## 予約確定方式の施設設定

テナントは宿泊施設ごとに予約確定方式を選択する。

| `booking_confirmation_mode` | 定義 |
| --- | --- |
| `instant` | 利用者の予約操作時に予約を即時確定する |
| `approval_required` | 利用者の予約申請後、テナントの承認で確定する |

初期値は`approval_required`とする。承認期限は`approval_deadline_hours`で設定し、初期値24時間、設定可能範囲は1〜72時間とする。`instant`では承認期限の設定値を使用しない。

予約を受け付ける施設は、予約受付期限とキャンセル条件の基準日時を確定するため`check_in_time`を必須とする。施設設定の適用方法と予約の状態遷移は予約仕様で定義する。

## 宿泊可能期間と予約受付期間

宿泊可能期間と予約受付期間は別の概念として管理する。

- 宿泊可能期間は、その施設で宿泊日として販売できる日付範囲を表す。
- 予約受付期間は、対象チェックイン日時に対して予約操作を受け付ける相対的な時間範囲を表す。

### 宿泊可能期間

`stay_available_starts_on`と`stay_available_ends_on`で半開区間`[starts_on, ends_on)`を表す。開始日は最初に宿泊できる日、終了日は最遅チェックアウト日であり、終了日当日の宿泊は含まない。

```text
stay_available_starts_on = 2026-08-01
stay_available_ends_on   = 2026-09-01

宿泊可能: 2026-08-01泊から2026-08-31泊まで
最遅チェックアウト: 2026-09-01
```

両方とも任意とし、片方だけの設定を許可する。両方を設定する場合は`starts_on < ends_on`とする。値が過去になっても履歴として保持し、過去日であることだけを理由に無効とはしない。

予約の全宿泊期間が設定範囲内に収まらなければならない。開始日がある場合は`check_in_date >= starts_on`、終了日がある場合は`check_out_date <= ends_on`とする。設定変更は新しい予約・予約申請だけに適用し、既存予約には遡及しない。

### 予約受付期間

`booking_open_days_before`はチェックインの何日前から受付を開始するかを表し、初期値365日、設定範囲は1〜365日とする。`booking_close_hours_before`はチェックインの何時間前に受付を終了するかを表し、初期値0時間、設定範囲は0〜720時間とする。どちらもテナントが宿泊施設ごとに設定できる。

```text
booking_opens_at  = check_in_at - booking_open_days_before 日
booking_closes_at = check_in_at - booking_close_hours_before 時間
```

予約操作日時は`booking_opens_at`以降かつ`booking_closes_at`より前でなければならない。受付可能な時間幅が正になるよう`booking_open_days_before × 24 > booking_close_hours_before`とする。

宿泊可能期間内でも予約受付期間外なら新規予約を受け付けない。反対に予約受付期間内でも、宿泊日が宿泊可能期間外なら受け付けない。設定変更は既存予約へ遡及しない。

宿泊可能期間を短縮する際、その変更後の期間外となる`requested / confirmed`予約が存在しても変更を許可し、既存予約は維持する。ただし保存前に影響する予約件数と、予約が自動キャンセルされないことを警告してテナントの確認を求める。

## タイムゾーン

日時を扱う基準として宿泊施設ごとに`time_zone`を持ち、初期値は`Asia/Tokyo`とする。同じテナントが異なる地域の施設を運営できるよう、テナント共通設定にはしない。

値はIANAタイムゾーン名とし、予約受付開始・終了、チェックイン開始、承認期限およびキャンセル期限の計算に使用する。タイムゾーン変更は新しい予約・予約申請から適用し、既存予約に保存済みのチェックイン日時、承認期限およびスナップショットには遡及しない。

## Rate PlanとRoom Type別料金

Rate Planは食事やキャンセル条件をまとめた施設固有の販売プランであり、テナントが自ら所有する宿泊施設ごとに作成する。

1つのRate Planを複数のRoom Typeへ適用でき、金額はRate PlanとRoom Typeの組み合わせごとに設定する。

```text
RatePlan: 朝食付き・キャンセル可
├─ スタンダードツイン: 15,000円
├─ デラックスツイン: 20,000円
└─ 和室: 18,000円
```

異なるRate Planを選んでも物理在庫は増えず、同じRoom Typeの共通在庫を消費する。Rate Planごとに在庫数を複製しない。

食事条件は`room_only / breakfast / dinner / breakfast_and_dinner / other`とする。Rate PlanとRoom Type別料金は無効化後も過去の予約から参照できる状態で保持する。

### Rate Plan固有の期間・泊数制限

初期仕様ではRate Planごとの次の制限を持たない。

- 最低宿泊数、最大宿泊数
- Rate Planを予約操作で選択できる販売期間
- Rate Planを適用できる宿泊対象期間
- チェックイン何日前までという早期予約期限

すべての公開中Rate Planは、施設共通の宿泊可能期間と予約受付期間に従い、期間内であれば1泊以上の任意の泊数に適用できる。Rate Planによって変わる条件は、初期仕様では食事、キャンセル条件およびRoom Type別料金だけとする。

連泊割引、早期予約、期間限定キャンペーンなどを提供する要件が確定した時点でRate Plan固有の制限を追加する。初期仕様では将来利用を想定したNULLカラムも追加しない。

## Room TypeとRate Planの公開・無効化

Room TypeとRate Planは、単純な有効フラグではなく`status`で公開ライフサイクルを管理する。

| `status` | 定義 |
| --- | --- |
| `draft` | 作成・編集中。一般ユーザーには表示せず、新規予約で選択できない |
| `published` | 公開中。ほかの販売条件も満たす場合に新規予約で選択できる |
| `inactive` | 公開停止。一般ユーザーには表示せず、新規予約で選択できない |

初期値は`draft`とする。Room Typeを`published`へ遷移するには、名称、説明、販売形態、定員、および販売形態に対応する有効な物理在庫を必須とする。貸切・個室は有効なRoomが1件以上、相部屋は有効なRoomに属する有効なBedが1件以上必要である。Amenitiesは任意とする。

Rate Planを`published`へ遷移するには、名称、食事条件およびキャンセル種別を必須とし、説明とRoom Type別料金は必須としない。Rate Plan単体を先に公開できるが、有効なRoom Type別料金と結び付くまでは予約候補にならない。

`draft / inactive`から`published`へ遷移する際は公開必須項目と関連データを再検証する。`published`から`inactive`への変更は即時に新規予約へ反映し、`inactive`からの再公開を許可する。

Room TypeとRate Planを`inactive`にしても、`requested / confirmed`を含む既存予約、料金・キャンセル条件のスナップショットおよび物理Room・Bedの割り当ては変更しない。

Room TypeとRate Planの組み合わせである`stay_room_type_rates`は、価格と関連が揃ったレコードだけを作成するため`status`を持たず、`active`で組み合わせ単位の販売可否を管理する。新規予約で選択するには、Room TypeとRate Planがともに`published`で、組み合わせが`active = true`でなければならない。

物理削除は`draft / inactive`で、関連するRoom、Bed、Room Type別料金および予約参照が存在しない場合だけ許可する。過去または現在の予約から参照されるレコードは物理削除せず`inactive`で保持する。

## キャンセルポリシーのテンプレート

Rate Planはキャンセル種別として`standard / non_refundable`のいずれかを持つ。専用テーブルは作成せず、初期仕様ではシステム固定テンプレートを使用する。テナントが期限や料率を自由設定する機能は持たない。

`standard`の固定料率は次のとおりとする。どの条件にも該当しない早期キャンセルは無料とする。

```text
168時間前以降: 20%
48時間前以降: 50%
24時間前以降: 80%
0時間前以降: 100%
無断不泊: 100%
```

`non_refundable`は予約確定後の利用者キャンセルを100%、無断不泊を100%とする。予約への条件の固定とキャンセル料計算は予約仕様で定義する。

## 宿泊料金

| 項目 | 定義 |
| --- | --- |
| 通貨 | 初期仕様は`JPY` |
| 金額の保持単位 | 日本円の整数 |
| 料金単位 | `entire_place / private_room`は1 Room・1泊、`shared_room`は1 Bed・1泊 |
| 消費税 | テナントが利用者向け料金へ反映し、システムは自動加算しない |
| 追加人数料金 | 初期仕様では扱わない |
| 清掃料金・手数料 | 初期仕様では扱わない |

Room TypeとRate Planの組み合わせに料金を設定する。初期仕様では`JPY`のみを許可し、画面に通貨選択を表示しない。

テナントは消費税を考慮した利用者向け1泊料金を入力する。システムは消費税を自動加算せず、税込・税抜を切り替える属性も持たない。追加人数料金、清掃料金、サービス料、宿泊税、入湯税および割引も初期仕様では扱わない。

### 日別料金

基本料金は`stay_room_type_rates.price_per_night_amount`に保持し、曜日、特定日、繁忙期などの日付別上書き料金は`stay_room_type_rate_daily_prices`へ保持する。日別料金はRate Plan単体ではなく、Room TypeとRate Planの組み合わせへ紐づける。

宿泊日ごとの適用料金は次の優先順位で決定する。

```text
対象のstay_dateに日別料金が存在する
  → stay_room_type_rate_daily_prices.price_amount

存在しない
  → stay_room_type_rates.price_per_night_amount
```

`stay_date`はその日に開始する1泊を表す。1つのRoom Type別料金と宿泊日の組み合わせには日別料金を1件だけ登録できる。日別料金を削除した場合は、販売停止にはせず基本料金へ戻す。

初期仕様では曜日ルールや繁忙期ルール自体をDBへ保存しない。管理画面で期間、曜日、料金を指定する一括設定を提供し、対象日ごとの日別料金を作成または更新する。これにより、曜日ルールと特定日ルールの優先順位を持たせず、最終的な日付別料金を一意にする。

日別料金は価格だけを管理し、販売停止や在庫数を持たない。販売停止は物理在庫停止またはRoom Typeの日別販売制御で扱う。Room Type、Rate PlanまたはRoom Type別料金が選択不可の場合、日別料金が存在しても予約できない。

日別料金の変更は新規予約だけに適用する。既存予約は予約時の`price_snapshot`に保存した日別料金を維持する。

将来複数通貨へ対応する場合はISO 4217の通貨コードを使用し、金額を最小通貨単位で保持する。予約時の料金計算とスナップショットは予約仕様で定義する。

### 設計判断の経緯

一般消費者へインターネット上で価格を事前表示する場合、原則として消費税を含む総額表示が求められる。詳細は[国税庁「事業者が消費者に対して価格を表示する場合の取扱い」](https://www.nta.go.jp/law/tsutatsu/kihon/shohi/18/01.htm)および[国税庁「総額表示の義務付け」](https://www.nta.go.jp/taxes/shiraberu/taxanswer/shohi/6902_qa.htm)を参照する。

システムが税を自動計算するには、販売・決済・請求の主体、テナントの課税区分、適用税率、端数処理を確定する必要がある。このため初期仕様ではテナントが利用者向け料金を決定し、システムは入力額を表示する。

## データモデルの責務

Room Type名は施設内で一意かつ最大100文字、説明は最大5,000文字とする。Rate Plan名は施設内で一意かつ最大100文字、説明は最大2,000文字とする。Amenity名は最大100文字とする。いずれも前後の空白を除去し、説明文はプレーンテキストとして扱う。

- `stay_listings`は予約確定方式、承認期限、時刻、宿泊可能期間、予約受付期間、ハウスルールを持つ。
- `stay_room_types`は名称、販売形態、定員、公開状態を持ち、料金、在庫数、Amenitiesの自由入力値は持たない。
- `stay_amenities`と2つの関連テーブルは、共通・テナント固有Amenitiesと施設・Room Typeへの設定を持つ。
- `stay_rooms / stay_beds`は物理在庫の根拠を持つ。
- `stay_room_blocks / stay_bed_blocks`は施設都合の停止期間を持つ。
- `stay_room_type_daily_sales_controls`は営業上のRoom Type別・宿泊日別販売上限を持つ。
- `stay_rate_plans`はプラン名、食事条件、キャンセル種別、公開状態を持つ。
- `stay_room_type_rates`はRoom TypeとRate Planの組み合わせと1泊料金を持つ。
- `stay_room_type_rate_daily_prices`はRoom TypeとRate Planの組み合わせに対する特定宿泊日の上書き料金を持つ。

## 公開条件

Stay Listingの公開条件と、指定日程に対する予約可否は分けて判定する。満室や一時的な全室停止だけを理由にListingを非公開にしない。

### Stay Listingの公開条件

共通条件に加えて、`draft / closed`から`published`へ遷移するには次をすべて満たさなければならない。

#### Listingと所在地

- `title`と`description`が入力されている
- 画像が1件以上存在する
- `listing_location`が存在する
- `prefecture / city / address_line1`が入力されている
- `latitude / longitude`が設定されている

`postal_code / address_line2 / google_place_id`は任意とする。住所を保持することと、一般ユーザーへ完全な住所を開示することは分けて扱い、開示範囲は位置情報仕様で定義する。

#### 宿泊施設設定

- `check_in_time / check_out_time`が設定されている
- `time_zone`が有効なIANAタイムゾーンである
- 予約確定方式、承認期限、予約受付開始日数、予約受付終了時間が許可値と整合条件を満たす
- 宿泊可能期間を両方設定する場合は開始日が終了日より前である
- 宿泊可能期間の終了日を設定する場合は、施設の現地日付より後であり、公開時点で未来の宿泊日が残っている

`house_rules`と宿泊可能期間の開始・終了は任意とする。

#### 販売可能セット

次の一連の販売可能セットが同じ宿泊施設内に1組以上必要である。

```text
status = published のRoom Type
＋ 販売形態に対応するactiveなRoomまたはBed
＋ status = published のRate Plan
＋ active = true のRoom Type別料金
＋ 1円以上のJPY料金
```

すべてのRoom TypeとRate Planを公開する必要はなく、未完成のものは`draft`、販売停止中のものは`inactive`のまま保持できる。

### 公開後の整合性

`status = published`のStay Listingは販売可能セットを常に1組以上維持しなければならない。最後の販売可能セットを失う次の操作は拒否し、先にListingを`closed`へ変更するよう案内する。

- 最後の公開Room TypeまたはRate Planを`inactive`にする
- 最後の有効なRoom Type別料金を無効化する
- 最後の有効な物理RoomまたはBedを無効化する
- 公開必須項目を未入力または不正な値へ変更する

子レコードの更新によってListingを暗黙的に`closed`へ変更しない。テナントがListingの受付終了を明示的に行った後で、販売可能セットをなくす変更を許可する。

### 指定日程の予約可否

公開中のListingでも、利用者が指定した日程ごとに次をすべて満たす場合だけ予約可能とする。

- 宿泊可能期間内である
- 予約受付期間内である
- Room TypeとRate Planが`published`である
- Room Type別料金が`active`である
- 対応するRoomまたはBedが有効である
- 施設停止およびほかの予約と期間が重複しない

指定日程が満室または全室停止でもListingは`published`のまま維持し、その日程では予約不可として表示する。

## テスト条件

- 自テナントの施設にのみRoom Type、Room、Bed、Rate Plan、Room Type別料金を作成・更新できること。
- Room TypeとRoom、RoomとBedが同じ施設および許可された販売形態で紐づくこと。
- 貸切・個室はRoom、相部屋はBedを基本在庫として数えること。
- Room・Bedの停止期間と予約割り当て期間を重複させられないこと。
- 日別販売上限が0以上で、Room Typeと宿泊日の組み合わせで一意であること。
- 日別販売上限0で販売停止となり、レコード削除で物理在庫数までの販売へ戻ること。
- 既存予約数を下回る上限設定で警告し、既存予約を維持して新規予約数を0にすること。
- 販売上限が物理在庫数を超えても実際の予約可能数が物理空き数を超えないこと。
- 期間・曜日による販売上限の一括設定が対象日だけを作成または更新すること。
- 公開するRoom Typeの`capacity`が1以上で、相部屋では1であること。
- Room Typeは名称、説明、販売形態、定員および対応する有効な物理在庫がなければ公開できないこと。
- Amenitiesなしでも施設とRoom Typeを公開できること。
- テナントが共通Amenitiesを変更できず、自テナント固有Amenitiesだけを作成・変更・無効化できること。
- Amenitiesの`scope`に適合する施設・Room Typeだけへ関連付けられること。
- 他テナント固有Amenitiesを選択できず、共通コードとテナント固有コードが衝突しないこと。
- 無効化したAmenitiesが新規選択、現在の表示、検索から除外され、既存関連は保持されること。
- 複数のRoom Type AmenitiesによるAND検索を同じRoom Type内で判定すること。
- Rate Planは名称、食事条件、キャンセル種別がなければ公開できず、説明とRoom Type別料金なしでも単体公開できること。
- Rate PlanとRoom Typeが同じ施設に属し、その組み合わせを重複登録できないこと。
- すべてのRate Planが施設共通の宿泊可能期間と予約受付期間に従い、1泊以上の予約へ適用できること。
- Room TypeとRate Planの初期状態が`draft`で、許可された状態遷移だけを行えること。
- Room TypeとRate Planの一方でも`published`でない場合は新規予約で選択できないこと。
- `inactive`への変更が新規予約だけに反映され、既存予約と割り当てへ影響しないこと。
- 公開条件を満たす`inactive`レコードを再公開できること。
- 関連データまたは予約参照があるRoom TypeとRate Planを物理削除できないこと。
- `cancellation_policy_type`が`standard / non_refundable`だけを許可すること。
- Room Type別料金が1以上の整数かつ`JPY`であること。
- 日別料金が1以上の整数で、Room Type別料金と宿泊日の組み合わせで一意であること。
- 日別料金がある日は上書き料金、ない日は基本料金を適用すること。
- 日別料金を削除すると基本料金へ戻り、販売停止にはならないこと。
- 期間・曜日による一括設定が対象日だけを作成または更新すること。
- 日別料金の変更が既存予約の料金スナップショットへ遡及しないこと。
- 予約確定方式と承認期限時間が許可値・境界値を満たすこと。
- 宿泊可能期間の片側だけを設定でき、両方を設定する場合は開始日が終了日より前であること。
- 予約の全宿泊期間が宿泊可能期間内に収まること。
- 予約受付期間の開始・終了境界と初期値を検証すること。
- 受付開始日数が1〜365、受付終了時間が0〜720で、受付時間幅が正であること。
- 宿泊可能期間または予約受付期間の一方でも範囲外なら予約を受け付けないこと。
- 期間設定を変更しても既存予約へ遡及しないこと。
- 既存予約が期間外になる短縮では影響件数を警告し、確認後も既存予約を維持すること。
- IANAタイムゾーンだけを設定でき、初期値が`Asia/Tokyo`であること。
- タイムゾーン変更が既存予約の保存済み日時とスナップショットへ遡及しないこと。
- Listing、所在地、施設設定および販売可能セットの全公開条件を満たす場合だけStay Listingを公開できること。
- 下書きまたは無効なRoom TypeとRate Planが混在しても、販売可能セットが1組あれば公開できること。
- 公開中に最後の販売可能セットまたは公開必須項目を失う更新を拒否すること。
- Listingを受付終了した後は販売可能セットをなくす更新を許可すること。
- 指定日程が満室または全室停止でもListingを公開状態に維持し、その日程だけ予約不可になること。
