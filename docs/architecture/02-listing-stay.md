# 滞在Listing定義

## 目的

滞在Listingにおける施設、部屋、物理在庫、料金プランおよび予約受付設定の責務を定義する。個別予約の受付、状態遷移、物理在庫の割り当て、宿泊者、料金・キャンセル条件のスナップショットは [`02-stay-reservation.md`](./02-stay-reservation.md) を参照する。

テーブル構造は [`../er/01-listing-stay.md`](../er/01-listing-stay.md) を正本とする。Listing共通仕様は [`02-listing.md`](./02-listing.md)、住所・位置情報は [`03-location.md`](./03-location.md) を参照する。

## 宿泊施設・部屋・在庫の単位

1つのListingは、テナントが運営する1つの宿泊施設を表す。施設は1つ以上のRoom Typeを持ち、一般ユーザーは物理的な部屋ではなくRoom Typeを選択する。

Room Typeはシステム共通マスターではなく、テナントが自ら所有する宿泊施設ごとに作成する販売上の部屋分類とする。同じ名称でも施設が異なれば別のRoom Typeとして扱う。テナントは自ら所有する施設にのみRoom Typeを作成・更新できる。

物理的な宿泊空間はRoomとして登録し、同じ施設に属する1つのRoom Typeへ紐づける。一般ユーザーにはRoomを選択させない。

```text
Tenant
└─ Listing（宿泊施設）
   └─ StayListing（施設共通の宿泊情報）
      ├─ RoomType（販売上の部屋分類）
      │  └─ Room（物理的な部屋）
      │     └─ Bed（相部屋内の物理的なベッド）
      └─ RatePlan（食事・キャンセル等の販売条件）
```

| `room_kind` | 販売形態 | 販売・在庫の単位 |
| --- | --- | --- |
| `entire_place` | 一棟または独立した空間を貸し切る | Room |
| `private_room` | 施設内の個室を貸し切る | Room |
| `shared_room` | 他の宿泊者と共有する相部屋 | Bed |

1つのRoom TypeでRoom単位とBed単位の販売を混在させない。物理在庫を登録するため、Room Typeに手入力の在庫数は持たない。`entire_place / private_room`の基本在庫は有効なRoom数、`shared_room`は有効なBed数から算出する。一棟貸しは一棟を表すRoomを1件登録する。

## 物理在庫の停止

施設都合による一時停止は、RoomまたはBedと停止期間を紐づけて管理する。`active`は恒久的な有効・無効に使用し、修繕、清掃、手動停止など日付を伴う停止には使用しない。

停止期間はチェックイン日を含みチェックアウト日を含まない半開区間として扱う。同じRoomまたはBedの停止期間同士は重複を許可するが、予約へ割り当て済みの期間と重複する停止は作成できない。

Room Type単位の日別販売上限は初期仕様では定義しない。物理在庫数より少ない数だけを販売する要件が確定した場合に追加する。

## Room Typeの定員

Room Typeの`capacity`は、1つの販売在庫単位へ宿泊できる最大人数を表す。公開するRoom Typeでは必須かつ1以上とする。

| `room_kind` | 1販売在庫単位 | `capacity` |
| --- | --- | --- |
| `entire_place / private_room` | Room | 1 Roomあたりの最大宿泊人数 |
| `shared_room` | Bed | 1固定 |

相部屋の物理Room全体の収容人数は、そのRoomに属する有効なBed数から算出し、Room Typeの`capacity`には持たない。予約人数の検証は予約仕様で定義する。

## 予約確定方式の施設設定

テナントは宿泊施設ごとに予約確定方式を選択する。

| `booking_confirmation_mode` | 定義 |
| --- | --- |
| `instant` | 利用者の予約操作時に予約を即時確定する |
| `approval_required` | 利用者の予約申請後、テナントの承認で確定する |

初期値は`approval_required`とする。承認期限は`approval_deadline_hours`で設定し、初期値24時間、設定可能範囲は1〜72時間とする。`instant`では承認期限の設定値を使用しない。

`approval_required`で予約を受け付ける施設は`check_in_time`を必須とする。施設設定の適用方法と予約の状態遷移は予約仕様で定義する。

## Rate PlanとRoom Type別料金

Rate Planは食事やキャンセル条件をまとめた施設固有の販売プランであり、テナントが自ら所有する宿泊施設ごとに作成する。

1つのRate Planを複数のRoom Typeへ適用でき、金額はRate PlanとRoom Typeの組み合わせごとに設定する。

```text
RatePlan: 朝食付き・キャンセル可
├─ スタンダードツイン: 15,000円
├─ デラックスツイン: 20,000円
└─ 和室: 18,000円
```

異なるRate Planを選んでも物理在庫は増えず、同じRoom Typeの共通在庫を消費する。Rate Planごとに在庫数を複製しない。

食事条件は`room_only / breakfast / dinner / breakfast_and_dinner / other`とする。Rate PlanとRoom Type別料金は無効化後も過去の予約から参照できる状態で保持する。

## キャンセルポリシーのテンプレート

Rate Planはキャンセル種別として`standard / non_refundable`のいずれかを持つ。専用テーブルは作成せず、初期仕様ではシステム固定テンプレートを使用する。テナントが期限や料率を自由設定する機能は持たない。

`standard`の固定料率は次のとおりとする。どの条件にも該当しない早期キャンセルは無料とする。

```text
168時間前以降: 20%
48時間前以降: 50%
24時間前以降: 80%
0時間前以降: 100%
無断不泊: 100%
```

`non_refundable`は予約確定後の利用者キャンセルを100%、無断不泊を100%とする。予約への条件の固定とキャンセル料計算は予約仕様で定義する。

## 宿泊料金

| 項目 | 定義 |
| --- | --- |
| 通貨 | 初期仕様は`JPY` |
| 金額の保持単位 | 日本円の整数 |
| 料金単位 | `entire_place / private_room`は1 Room・1泊、`shared_room`は1 Bed・1泊 |
| 消費税 | テナントが利用者向け料金へ反映し、システムは自動加算しない |
| 追加人数料金 | 初期仕様では扱わない |
| 清掃料金・手数料 | 初期仕様では扱わない |

Room TypeとRate Planの組み合わせに料金を設定する。初期仕様では`JPY`のみを許可し、画面に通貨選択を表示しない。

テナントは消費税を考慮した利用者向け1泊料金を入力する。システムは消費税を自動加算せず、税込・税抜を切り替える属性も持たない。追加人数料金、清掃料金、サービス料、宿泊税、入湯税および割引も初期仕様では扱わない。

将来複数通貨へ対応する場合はISO 4217の通貨コードを使用し、金額を最小通貨単位で保持する。予約時の料金計算とスナップショットは予約仕様で定義する。

### 設計判断の経緯

一般消費者へインターネット上で価格を事前表示する場合、原則として消費税を含む総額表示が求められる。詳細は[国税庁「事業者が消費者に対して価格を表示する場合の取扱い」](https://www.nta.go.jp/law/tsutatsu/kihon/shohi/18/01.htm)および[国税庁「総額表示の義務付け」](https://www.nta.go.jp/taxes/shiraberu/taxanswer/shohi/6902_qa.htm)を参照する。

システムが税を自動計算するには、販売・決済・請求の主体、テナントの課税区分、適用税率、端数処理を確定する必要がある。このため初期仕様ではテナントが利用者向け料金を決定し、システムは入力額を表示する。

## データモデルの責務

- `stay_listings`は予約確定方式、承認期限、時刻、予約可能期間、ハウスルールを持つ。
- `stay_room_types`は名称、販売形態、定員、設備を持ち、料金や在庫数は持たない。
- `stay_rooms / stay_beds`は物理在庫の根拠を持つ。
- `stay_room_blocks / stay_bed_blocks`は施設都合の停止期間を持つ。
- `stay_rate_plans`はプラン名、食事条件、キャンセル種別を持つ。
- `stay_room_type_rates`はRoom TypeとRate Planの組み合わせと1泊料金を持つ。

## 公開条件

共通の公開条件に加える滞在固有条件は要定義とする。予約を受け付けるには、選択可能なRoom Type、販売形態に対応する有効な物理在庫、および選択可能なRate PlanとRoom Type別料金が少なくとも1組必要である。`booking_confirmation_mode = approval_required`の場合はチェックイン時刻も必須とする。

## テスト条件

- 自テナントの施設にのみRoom Type、Room、Bed、Rate Plan、Room Type別料金を作成・更新できること。
- Room TypeとRoom、RoomとBedが同じ施設および許可された販売形態で紐づくこと。
- 貸切・個室はRoom、相部屋はBedを基本在庫として数えること。
- Room・Bedの停止期間と予約割り当て期間を重複させられないこと。
- 公開するRoom Typeの`capacity`が1以上で、相部屋では1であること。
- Rate PlanとRoom Typeが同じ施設に属し、その組み合わせを重複登録できないこと。
- `cancellation_policy_type`が`standard / non_refundable`だけを許可すること。
- Room Type別料金が1以上の整数かつ`JPY`であること。
- 予約確定方式と承認期限時間が許可値・境界値を満たすこと。
- 滞在固有の公開条件を満たす場合と満たさない場合を検証すること。
