# 宿泊予約定義

## 目的

宿泊予約の受付、承認、物理在庫の割り当て、宿泊者、料金とキャンセル条件の固定、および状態遷移を定義する。

予約テーブル構造は [`../er/02-stay-reservation.md`](../er/02-stay-reservation.md)、宿泊施設、Room Type、物理在庫、Rate Planの定義は [`02-listing-stay.md`](./02-listing-stay.md) を正本とする。

## 予約番号

予約は内部主キーとは別に、利用者、Tenant Memberおよび通知で共通して使用する変更不可の`reservation_number`を持つ。DBの連番ID、作成日時、テナントIDその他の推測可能な値を番号へ埋め込まない。

形式は`ST-XXXX-XXXX-XXXX`とし、`X`にはCrockford Base32から紛らわしい`I / L / O / U`を除いた大文字12文字を使用する。

```text
ST-7K3M-9Q2X-R4WT
```

暗号学的に安全な乱数で生成し、DBの一意制約へ抵触した場合は最大5回再生成する。5回失敗した場合は予約作成全体をロールバックする。予約申請と即時予約のどちらも作成時に採番し、承認・拒否・取消後も変更しない。予約置換で作成する新予約には新しい予約番号を採番する。

検索入力では英字の大小、ハイフンおよび空白の違いを正規化するが、検索は正規化後の完全一致だけとする。前方一致・部分一致検索は提供しない。予約番号は認証情報ではないため、番号が一致しても次の認可を必須とする。

- 一般ユーザーは自分が作成した予約だけを参照できる。
- Tenant Memberは自テナントが所有するListingの予約だけを参照できる。
- 運営管理者は予約参照権限を持つロールに限定する。

## 宿泊期間と物理在庫の割り当て

宿泊期間はチェックイン日を含みチェックアウト日を含まない半開区間`[check_in_date, check_out_date)`として扱う。8月1日チェックイン・8月3日チェックアウトは8月1日泊と8月2日泊の在庫を使用する。

期間の重複は次の条件で判定する。

```text
既存の開始日 < 新しい終了日
かつ
既存の終了日 > 新しい開始日
```

予約の全宿泊期間は施設の宿泊可能期間に収まり、予約操作日時は施設の予約受付期間内でなければならない。宿泊可能期間と予約受付期間の定義は [`02-listing-stay.md`](./02-listing-stay.md) を参照する。日時の計算には予約作成時点の施設タイムゾーンを使用する。

予約受付時に、選択されたRoom Typeに属する空きRoomまたはBedをシステムが自動で割り当てる。Room Type単位の数量だけを確保した未割り当て状態は作らない。

割り当て対象は予約期間全体で次を満たさなければならない。

- `active = true`
- 予約されたRoom Typeに所属する
- 有効期限内の`requested`または`confirmed`予約と期間が重複しない
- RoomまたはBedの施設停止期間と重複しない

貸切・個室はRoom、相部屋はBedを`quantity`件割り当てる。連泊では同じ物理在庫を使用し、宿泊途中で分割しない。

各宿泊日の予約可能数は、物理在庫とRoom Typeの日別販売上限の両方から算出する。有効期限内の`requested`と`confirmed`へ割り当てられたRoomまたはBedの件数を`used_count`とする。

```text
physical_available
= max(activeかつ停止されていない物理在庫数 - used_count, 0)

日別販売制御なし:
available = physical_available

日別販売制御あり:
sales_remaining = max(sales_limit - used_count, 0)
available = min(physical_available, sales_remaining)
```

連泊予約では、すべての宿泊日について`available >= quantity`を満たし、かつ期間全体で同じ物理在庫を確保できなければならない。どのRate Planを選択しても、同じRoom Typeの日別販売上限と共通物理在庫を消費する。

予約受付時はRoom Typeを先にロックし、対象日の販売制御、使用数、物理空き数を再計算する。その後に候補となる物理在庫をロックし、割り当てと予約状態の保存を同一トランザクションで行う。日別販売制御レコードが存在しない日もRoom Typeをロックし、同時予約による上限超過を防ぐ。必要数を確保できなければ予約または予約申請を成立させない。

テナントは確定後も同じRoom Typeに属する空きRoomまたはBedへ割り当てを変更できる。変更先のロック、利用可能性の確認、割り当ての更新を同一トランザクションで行い、失敗時は元の割り当てを維持する。別のRoom Typeへの変更は予約内容の変更として扱う。

## 予約内容の変更

初期仕様では、日程、数量、宿泊人数、Room TypeまたはRate Planを既存予約上で直接変更しない。これらの変更は、現在の在庫・料金・キャンセル条件で新しい予約を作成し、成立後に旧予約を`canceled`へ遷移させる「予約の置換」として扱う。

代表宿泊者・同行者の変更と、同じRoom Type内の物理Room・Bed割り当て変更は予約条件の置換に含めない。変更期限と履歴は別途定義する。

### 置換処理

置換は次の順序で行う。

1. 旧予約と対象Room Typeをロックする。
2. 変更後の条件で宿泊提供期間、予約受付期間、定員、販売上限、物理在庫、料金およびキャンセル条件を再評価する。
3. 新予約、新しい料金・キャンセル条件のスナップショット、および新しい物理在庫割り当てを作成する。
4. 新予約が成立した後、旧予約を`canceled`へ遷移させる。
5. 旧予約の`replaced_by_reservation_id`へ新予約を設定する。

全処理を同一トランザクションで行う。新予約の作成または物理在庫確保に失敗した場合はすべてをロールバックし、旧予約の状態、料金スナップショットおよび割り当てを維持する。

置換元にできるのは、有効期限内の`requested`または`confirmed`だけとする。`rejected / canceled / expired / completed / no_show`および既に置換先を持つ予約は置換できない。

在庫判定では、置換元の旧予約が確保している数量と物理Room・Bedだけを使用数から一時的に除外できる。他の予約が確保している在庫は除外しない。置換元と置換先が同一期間・同一Room Typeの場合は、旧予約の割り当てを新予約へ引き継いでもよい。

### 置換後の状態

- 旧予約が`requested`の場合、新予約は施設の予約確定方式に従って`requested`または`confirmed`で作成する。
- 旧予約が`confirmed`の場合、新予約も`confirmed`で作成し、承認制の施設ではテナントが変更内容を確認した操作として扱う。利用者だけで確定予約を置換するセルフサービスは初期仕様に含めない。
- 旧予約の取消には利用者キャンセル料を適用しない。新旧予約の料金差は表示・記録するが、初期仕様では差額の請求・返金を行わない。
- 置換済みの旧予約を再度置換できない。さらに変更する場合は、現在有効な置換先予約を新たな置換元とする。
- 新予約は作成時点の料金とキャンセル条件を新しいスナップショットへ固定し、旧予約のスナップショットを複製または更新しない。

## 宿泊人数と定員

`guest_count`は必須かつ1以上とする。初期仕様では年齢区分を持たず、宿泊する全員を1人として数える。料金計算には使用しない。

| `room_kind` | 予約条件 |
| --- | --- |
| `entire_place / private_room` | `guest_count <= capacity × quantity` |
| `shared_room` | `guest_count = quantity` |

貸切・個室は定員未満の人数で複数Roomを予約できる。相部屋は1人につき1 Bedを確保する。予約時に検証したRoom Typeの定員、宿泊人数、数量を`price_snapshot`へ複製し、Room Typeの定員変更を既存予約へ遡及させない。

## 予約者と宿泊者

`stay_reservations.user_id`は予約操作を行った予約者を表す。実際の宿泊者は予約者と同一とは限らないため、`stay_reservation_guests`へ予約時点の情報を保存する。

予約時に代表宿泊者1名の氏名、メールアドレス、電話番号を必須とする。予約者本人でなくてもよい。ユーザー情報を入力初期値にできるが、保存後は同期せず予約時点の連絡先を維持する。

同行者は氏名だけを持つ任意情報とし、予約時に全員分を求めない。予約後もチェックインまで追加、変更、削除でき、未登録でも予約の成立、承認、在庫確保に影響しない。

代表宿泊者は常に1名とし、削除は許可しない。代表宿泊者を含む登録済み宿泊者数は`guest_count`以下とするが、一致は必須としない。初期仕様では年齢区分、性別、住所、本人確認書類を保持しない。

### 宿泊者情報の変更期限

予約者本人と対象ListingのTenant Memberは、予約状態が`requested / confirmed`かつ操作日時が予約へ固定した`check_in_at`より前の場合だけ、代表宿泊者と同行者を変更できる。`check_in_at`ちょうどから変更不可とする。

変更できる内容は次のとおりとする。

- 代表宿泊者の氏名、メールアドレス、電話番号
- 同行者の追加、氏名変更、削除

代表宿泊者の削除、代表者なしの保存、登録済み宿泊者数が`guest_count`を超える変更は許可しない。`guest_count`自体は予約条件であるため、この操作では変更できず、変更する場合は予約置換を使用する。

変更は予約の料金、キャンセル条件、在庫、承認期限および状態へ影響させない。すべての宿泊者変更を同一トランザクションで保存し、`guest_updated`イベントを1件追加する。イベントには個人情報の変更前後値を複製せず、操作者と変更日時だけを記録する。

代表宿泊者のメールアドレスを変更した場合は、変更前と変更後の両方へ変更通知メールを送信する。メール送信失敗で変更処理をロールバックせず、通知の再送方針に従う。チェックイン開始後の訂正はPMS領域として初期仕様の画面では扱わない。

## 到着予定日時

予約者は予約時に任意で`expected_arrival_at`を入力できる。これは宿泊者が申告した到着予定日時であり、施設のチェックイン受付開始を表す`check_in_at`とは別の情報とする。未定の場合はNULLを許可し、予約の成立・承認・在庫確保には影響させない。

利用者画面では自由入力させず、「未定」と、予約作成時点の施設の`check_in_time`から`latest_check_in_time`までを1時間間隔で生成した時刻から選択させる。時刻を選択した場合は`check_in_date`と組み合わせ、予約へ固定した施設タイムゾーンで`expected_arrival_at`として保存する。アプリケーションは保存時にも選択肢に含まれる時刻かを検証する。

予約ダッシュボードの到着予定は`expected_arrival_at`がある予約をその時刻順に表示し、NULLは「到着時刻未定」として末尾に表示する。`check_in_at`を宿泊者の到着予定時刻として表示しない。

到着予定日時の予約後変更は、予約状態が`requested / confirmed`かつ現在日時が`check_out_at`未満の場合に、予約者本人または対象ListingのTenant Memberへ許可する。変更時は`arrival_time_updated`イベントを追記するが、料金、在庫、承認期限および予約状態は変更しない。

## 予約確定方式と承認期限

施設の`booking_confirmation_mode`に従って予約を作成する。

| 設定 | 作成時の処理 |
| --- | --- |
| `instant` | 在庫を割り当て、`confirmed`で作成する |
| `approval_required` | 在庫を仮確保し、`requested`で作成する |

即時確定では割り当てと予約作成を同一トランザクションで行い、`requested`を経由しない。

予約作成時に施設の`time_zone`と、`check_in_date`、`check_in_time`から`check_in_at`、`check_out_date`、`check_out_time`から`check_out_at`を算出して予約へ固定する。承認制の`approval_expires_at`は、申請日時に施設の承認期限時間を加えた日時と`check_in_at`の早い方とする。

```text
approval_expires_at
= min(申請日時 + approval_deadline_hours, チェックイン開始日時)
```

算出値は予約へ保存し、施設の時刻やタイムゾーンの変更を遡及させない。`check_in_at`以降は申請を受け付けない。キャンセル期限には`check_in_at`、宿泊完了の判定には`check_out_at`を使用する。

有効期限内の`requested`は在庫を消費する。テナントの承認で割り当てを維持したまま`confirmed`へ遷移する。拒否、利用者取消、承認期限切れでは在庫を解放する。期限を過ぎた申請は承認できず、期限切れ処理前でも在庫確保中とは扱わない。

## 予約ステータス

| 値 | 状態 |
| --- | --- |
| `requested` | テナント承認待ち、承認期限まで在庫を仮確保 |
| `confirmed` | 予約確定、在庫を確保済み |
| `rejected` | テナントによる予約拒否 |
| `canceled` | キャンセル |
| `expired` | 承認期限切れ |
| `completed` | 宿泊完了 |
| `no_show` | 予約は確定していたが宿泊者が現れなかった |

在庫を消費するのは有効期限内の`requested`と`confirmed`だけとする。`completed / no_show`を含む終端状態でも、割り当てレコードは履歴参照のため保持する。

### 宿泊完了と無断不泊

PMSのチェックイン・チェックアウト実績を持たない初期仕様では、`completed`と`no_show`へ自動遷移させない。対象Listingを所有するテナントの有効なTenant Memberが予約詳細から明示的に確定する。

| 遷移 | 実行可能条件 |
| --- | --- |
| `confirmed` → `completed` | 現在日時が予約へ固定した`check_out_at`以降 |
| `confirmed` → `no_show` | 現在日時が予約へ固定した`check_in_at`以降 |

無断不泊は宿泊施設が到着状況を確認したうえで判断する。チェックイン開始直後の誤操作を避けるため、画面で宿泊者氏名、日程、割り当て、キャンセル料100%を再表示し、確認操作を必須とする。

`completed`と`no_show`は終端状態とし、利用者による取消、予約置換、宿泊者情報変更および割り当て変更を許可しない。初期仕様では状態訂正を画面提供せず、誤操作時は運営管理者による個別対応とする。

`no_show`ではキャンセル条件スナップショットの`no_show_penalty_rate`を適用し、`accommodation_subtotal_amount`を基準にキャンセル料を計算してイベントへ記録する。初期テンプレートでは種別によらず100%となる。`completed`のキャンセル料はNULLとする。

`no_show`確定時は、予約者へのアプリ内通知と代表宿泊者へのメール通知を作成し、無断不泊として記録されたこと、適用料率・金額、問い合わせ案内を表示する。送信と再試行はテナント都合取消と同じ通知処理を使用する。

## 状態変更履歴と操作理由

`stay_reservations.status`は現在状態の参照に使用し、状態変更の経緯は追記専用の`stay_reservation_events`へ保存する。予約作成を含むすべての状態変更でイベントを1件作成し、予約本体の状態更新、イベント作成および在庫の確保・解放を同一トランザクションで行う。

イベントは作成後に更新・削除しない。誤操作の訂正は既存イベントを書き換えず、許可された状態遷移を新しいイベントとして追加する。状態だけを更新してイベントを作成しない処理は許可しない。

### イベント種別

| `event_type` | 状態遷移 | 操作者 |
| --- | --- | --- |
| `created` | なし → `requested / confirmed` | `user` |
| `approved` | `requested` → `confirmed` | `tenant_member` |
| `rejected` | `requested` → `rejected` | `tenant_member` |
| `canceled_by_user` | `requested / confirmed` → `canceled` | `user` |
| `canceled_by_tenant` | `requested / confirmed` → `canceled` | `tenant_member` |
| `expired` | `requested` → `expired` | `system` |
| `replaced` | `requested / confirmed` → `canceled` | `user / tenant_member` |
| `completed` | `confirmed` → `completed` | `tenant_member` |
| `no_show` | `confirmed` → `no_show` | `tenant_member` |
| `guest_updated` | 状態変更なし | `user / tenant_member` |
| `arrival_time_updated` | 状態変更なし | `user / tenant_member` |

### 操作者

イベントは`actor_type = user / tenant_member / system`を持つ。`guest_updated`では`from_status`と`to_status`へ操作時点の同じ予約状態を保存する。

- `user`では予約者本人の`user_id`を必須とし、`tenant_member_id`はNULLとする。
- `tenant_member`では対象Listingを所有するテナントの有効な`tenant_member_id`を必須とし、`user_id`はNULLとする。
- `system`では両方をNULLとする。

テナント画面では担当者としてTenant Memberの表示名を表示する。システム処理は「システム」と表示する。

### 理由

承認、予約作成および期限切れでは理由入力を求めない。拒否とテナント都合取消では`reason_code`を必須、利用者取消では任意とする。

| 操作 | `reason_code` |
| --- | --- |
| 拒否 | `unable_to_accommodate / request_not_acceptable / facility_unavailable / other` |
| テナント都合取消 | `facility_unavailable / maintenance / overbooking / safety / other` |
| 利用者取消 | `plans_changed / schedule_changed / booked_elsewhere / other` |
| 予約置換 | `reservation_replaced`固定 |

`reason_detail`は相手方へ表示できる説明、`internal_note`はテナント内部だけで参照するメモとする。`reason_code = other`では`reason_detail`を必須とする。`internal_note`を入力できるのはTenant Memberだけとする。理由詳細へ本人確認情報、決済情報その他の機微情報を記載しないよう画面で案内する。

### キャンセル料の記録

取消イベントと`no_show`イベントは`cancellation_penalty_amount`を持つ。確定予約の利用者取消と`no_show`ではキャンセル条件スナップショットから算出した金額を必須とする。申請中の利用者取消、テナント都合取消および予約置換では0とする。それ以外のイベントではNULLとする。

## テナント都合取消の通知

テナントが予約を取り消した場合、予約者へのアプリ内通知と、取消時点で予約に保存されている代表宿泊者メールアドレスへのメール通知を必須とする。SMS、プッシュ通知および電話連絡の記録は初期対象外とする。

通知には少なくとも次を含める。

- 施設名と予約を識別できる情報
- チェックイン日、チェックアウト日、Room Type、Rate Plan
- 施設都合で取消されたこと
- 利用者向けの理由コード表示名と`reason_detail`
- キャンセル料が0円であること
- 初期仕様では決済・返金を処理しない旨と、必要な場合の問い合わせ案内

`internal_note`は通知へ含めない。理由コードは内部値をそのまま表示せず、利用者向けの日本語表示名へ変換する。

### 通知処理

予約を`canceled`へ遷移するトランザクション内で、`canceled_by_tenant`イベントと各通知経路の`stay_reservation_notifications`を作成する。アプリ内通知は`sent`、メール通知は`pending`で作成し、外部メール送信はトランザクションのコミット後に非同期ジョブで行う。通知レコード作成に失敗した場合は取消全体をロールバックするが、コミット後の送信失敗では取消を戻さない。

通知はイベント、通知種別、経路および宛先単位の冪等キーを持ち、同じ取消操作による重複送信を防ぐ。送信失敗は指数バックオフで最大5回再試行し、すべて失敗した場合は`failed`としてテナントの予約詳細に警告する。手動再送では同じ通知レコードを再利用し、送信履歴と試行回数を保持する。

アプリ内通知は予約者のUserへ紐づけて保存し、既読日時を持つ。メールの宛先は、後から宿泊者情報が変わっても送信対象を再現できるよう通知作成時に文字列として固定する。通知本文の再現に必要な施設名、日程、理由および金額も`payload_snapshot`へ固定し、ルートにスキーマの`version`を必須で保存する。

## 予約時料金のスナップショット

予約または予約申請の作成時に、利用者へ提示した料金と計算根拠を固定する。承認制でも申請時に固定し、承認時には再計算しない。

予約は`currency`、`accommodation_subtotal_amount`、`additional_fee_total_amount`、`discount_total_amount`、`total_amount`と、変更不可の`price_snapshot`を持つ。初期仕様では追加料金と割引を扱わず、両方の合計を0とする。

```text
accommodation_subtotal_amount = 各宿泊日の unit_amount × quantity の合計
total_amount = accommodation_subtotal_amount
             + additional_fee_total_amount
             - discount_total_amount
```

`price_snapshot`はスキーマバージョン、通貨、料金単位、Room Type、Rate Plan、施設・Room TypeのAmenities、数量、宿泊人数、日別料金明細、各合計を保持する。名称、販売形態、定員、食事条件も複製し、元レコードの変更や無効化後も予約時の内容を再現できるようにする。

```json
{
  "version": 1,
  "currency": "JPY",
  "pricing_unit": "room",
  "room_type": {
    "id": 10,
    "name": "スタンダードツイン",
    "room_kind": "private_room",
    "capacity": 2,
    "amenities": [
      { "code": "private_bathroom", "name": "専用バスルーム" }
    ]
  },
  "facility_amenities": [
    { "code": "wifi", "name": "無料Wi-Fi" }
  ],
  "rate_plan": {
    "id": 20,
    "name": "朝食付き・キャンセル可",
    "meal_type": "breakfast"
  },
  "quantity": 2,
  "guest_count": 3,
  "nights": [
    {
      "stay_date": "2026-08-10",
      "unit_amount": 15000,
      "quantity": 2,
      "subtotal_amount": 30000
    },
    {
      "stay_date": "2026-08-11",
      "unit_amount": 18000,
      "quantity": 2,
      "subtotal_amount": 36000
    }
  ],
  "accommodation_subtotal_amount": 66000,
  "additional_fee_total_amount": 0,
  "discount_total_amount": 0,
  "total_amount": 66000
}
```

`pricing_unit`は貸切・個室で`room`、相部屋で`bed`とする。各宿泊日は、対象日の`stay_room_type_rate_daily_prices`が存在すればその上書き料金を使用し、存在しなければ`stay_room_type_rates.price_per_night_amount`を使用する。解決した単価を宿泊日ごとの明細へ保存する。

元のRoom Type別料金、Room Type、Rate Planが変更されても既存予約の料金とスナップショットは更新しない。同じRoom Type内の物理在庫割り当て変更でも料金は変えない。日程、数量、Room Type、Rate Planの変更時の再見積もりは予約変更ルールで定義する。

### スナップショットのスキーマバージョンと検証

`price_snapshot`、`cancellation_policy_snapshot`、`payload_snapshot`は、ルートに1以上の整数である`version`を必須で持つ。新規作成時はアプリケーションが対応する最新バージョンで保存し、バージョン番号を省略したデータを最新形式として暗黙に扱わない。

スナップショットは履歴を再現するための変更不可データである。新しい項目や計算方法を導入しても既存データを新バージョンへ書き換えず、旧バージョンを読み取り・表示・計算できる処理を維持する。例えば税・手数料を追加して料金形式をV2にした後も、V1の予約はV1の計算規則で扱う。

アプリケーションはスナップショットの種類と`version`に応じて、検証・表示・計算処理を明示的に振り分ける。責務の例は次のとおりとする。

- `PriceSnapshot::V1::Validator / Presenter`
- `CancellationPolicySnapshot::V1::Validator / Calculator`
- `ReservationNotificationPayload::V1::Validator / Presenter`

予約・イベント・通知の作成トランザクション内で、対応バージョンのスキーマを検証してから保存する。検証対象には必須キー、JSON上の型、列挙値、数値範囲、日付形式、日別明細、明細小計、合計、および通常カラムとの整合性を含める。キャンセル条件ではルールのしきい値・料率・計算基準を検証し、キャンセル料は対応バージョンのCalculatorだけで算出する。通知本文は対応バージョンのPresenterから生成する。

読み取り時に未対応の`version`、欠落または不正な構造を検出した場合、最新形式として推測して処理しない。データ整合性エラーとして記録・監視し、管理画面には制御されたエラーを表示する。特にキャンセル料算出など金額に関わる処理は実行を中止する。

JSONB内部の値を検索・集計の正とせず、予約検索や金額集計に必要な値は通常カラムに保持する。初期仕様ではスナップショットへのGINインデックスを設けない。

## キャンセルポリシーのスナップショット

予約作成時にRate Planのキャンセル種別と固定テンプレートの条件を`cancellation_policy_snapshot`へ複製する。現在のRate Planやシステム標準料率ではなく、スナップショットだけで判定する。

`standard`は、キャンセル日時が「チェックイン開始日時－しきい値」以降となるルールを対象とし、複数該当する場合は最も小さいしきい値の料率を適用する。どのルールにも該当しない早期キャンセルは無料とする。

```json
{
  "version": 1,
  "type": "standard",
  "basis": "accommodation_subtotal",
  "rules": [
    { "hours_before_check_in": 168, "penalty_rate": 20 },
    { "hours_before_check_in": 48, "penalty_rate": 50 },
    { "hours_before_check_in": 24, "penalty_rate": 80 },
    { "hours_before_check_in": 0, "penalty_rate": 100 }
  ],
  "no_show_penalty_rate": 100
}
```

`non_refundable`も`version`を持ち、`type`、`basis`、`penalty_rate = 100`、`no_show_penalty_rate = 100`を保持する。

キャンセル料は利用者による`confirmed`予約のキャンセルだけに適用する。`requested`中の利用者取消とテナント都合の取消は無料とする。`non_refundable`は確定後100%、無断不泊は種別によらず100%とする。

```text
キャンセル料
= floor(accommodation_subtotal_amount × penalty_rate / 100)
```

## テスト条件

- 宿泊期間を半開区間として在庫の重複を判定すること。
- 宿泊可能期間と予約受付期間の両方を満たす場合だけ予約を受け付けること。
- 同時予約で同じ物理在庫を重複割り当てせず、必要数不足時は処理全体をロールバックすること。
- 日別販売制御の有無、上限0、上限残数、物理空き数の各条件で予約可能数を正しく算出すること。
- 連泊の全宿泊日で販売上限と物理在庫を満たす場合だけ予約できること。
- 異なるRate Planの同時予約でもRoom Type共通の販売上限を超えないこと。
- 貸切・個室に`quantity`件のRoom、相部屋に`quantity`件のBedを割り当てること。
- 同じRoom Type内の割り当て変更に成功し、失敗時は元の割り当てを維持すること。
- 予約置換時に変更後の在庫と料金を再評価し、新予約の成立後だけ旧予約を取消すること。
- 予約置換に失敗した場合、旧予約の状態、スナップショットおよび割り当てを維持すること。
- 置換元予約の在庫だけを再利用でき、他予約の在庫を使用できないこと。
- 置換元から置換先を参照でき、置換済みの旧予約を再度置換できないこと。
- `guest_count`とRoom Typeの定員・販売形態の条件を検証すること。
- 代表宿泊者が常に1名で、登録済み宿泊者数が`guest_count`を超えないこと。
- `requested / confirmed`かつ`check_in_at`未満の場合だけ予約者本人または対象テナントのMemberが宿泊者情報を変更できること。
- 宿泊者情報の変更で予約条件と状態が変わらず、個人情報を含まない`guest_updated`イベントが作成されること。
- 代表宿泊者のメール変更時に変更前後の宛先へ通知が作成されること。
- 即時確定と承認制で、設定に応じた初期状態と在庫割り当てになること。
- 承認期限の境界、期限切れ、拒否、取消で在庫が正しく解放されること。
- 予約作成とすべての状態変更で、正しい変更前後状態、イベント種別、操作者および発生日時を持つイベントが同一トランザクションで作成されること。
- 操作者種別に対応するUserまたはTenant Memberだけが設定され、システムイベントでは両方がNULLになること。
- 拒否・テナント都合取消の理由と`other`の説明が必須になり、承認・期限切れでは不要であること。
- 取消主体と予約状態に応じたキャンセル料が取消イベントへ記録されること。
- 状態変更イベントを更新・削除できないこと。
- テナント都合取消とアプリ内・メール通知予定が同一トランザクションで作成され、通知予定の作成失敗時は取消もロールバックすること。
- 外部メール送信の失敗で取消状態を戻さず、冪等に最大5回再試行できること。
- テナント都合取消通知に内部メモを含めず、通知作成時の宛先と表示内容を保持すること。
- 予約時に日別料金、合計、表示条件およびキャンセル条件を各スナップショットへ保存すること。
- 予約時に施設とRoom Typeの有効なAmenitiesのコードと表示名を料金スナップショットへ保存すること。
- 日別上書き料金がある宿泊日と基本料金へフォールバックする宿泊日を含む予約で、日別明細と合計が正しいこと。
- Rate Plan、料金、定員、標準料率の変更を既存予約へ遡及させないこと。
- 予約時の施設タイムゾーンで`check_in_at`を固定し、施設の時刻・タイムゾーン変更を遡及させないこと。
- 予約番号が指定形式の安全な乱数から生成され、重複時に再生成され、予約作成後に変更されないこと。
- 予約番号検索が正規化後の完全一致かつ予約所有関係の認可を満たす場合だけ結果を返すこと。
- 予約時の施設タイムゾーンで`check_out_at`を固定し、施設の時刻・タイムゾーン変更を遡及させないこと。
- `check_out_at`以降だけ`completed`へ、`check_in_at`以降だけ`no_show`へ遷移でき、Tenant Member以外は実行できないこと。
- `no_show`で100%のキャンセル料とイベントが記録され、アプリ内・メール通知が作成されること。
- `completed / no_show`から状態変更、予約置換、宿泊者変更および割り当て変更ができないこと。
- キャンセル種別、状態、主体、時刻に応じた料率を適用し、1円未満を切り捨てること。
- 到着予定日時を任意で保存でき、入力時は予約時点のチェックイン受付時間から生成した1時間間隔の選択肢に含まれること。
- 到着予定一覧では申告時刻順に表示し、未入力予約を「到着時刻未定」として末尾に表示すること。
- 許可された期限内の到着予定日時変更で`arrival_time_updated`イベントを作成し、料金・在庫・状態を変更しないこと。
- すべてのスナップショットに作成時点の最新`version`が保存され、バージョン別の必須キー、型、列挙値および数値範囲を検証すること。
- 料金スナップショットの日別明細・合計と通常カラムの不一致、およびキャンセル条件の不正なしきい値・料率を保存できないこと。
- 新バージョン導入後も旧バージョンのスナップショットを変更せず、対応する旧版の表示・料金判定・キャンセル料計算を再現できること。
- `version`の欠落や未対応バージョンを最新形式として扱わず、金額に関わる処理を中止して整合性エラーとして扱うこと。
- 通知ペイロードをバージョン別に検証し、そのバージョンに対応する表示処理で通知本文を再現できること。
