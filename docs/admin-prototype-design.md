# 運営管理プロトタイプ UI 設計

## 目的と背景

テナント向けプロトタイプとは別に、Community Hub運営者がテナント、掲載情報、運営管理者を横断管理する画面を検証する。既存Rails Adminのテナントアカウント管理を基礎に、運営全体の状況と対応事項を把握できるUIへ拡張する。

## 認証・権限の前提

ER図と認可設計に従い、ログイン主体は `Account(account_type = admin)` と、それに1対1で紐づく `Admin(role = super_admin, status = active)` とする。プロトタイプはsuper_adminでログイン中の想定とし、テナント画面のAccount・TenantMemberとは状態を共有しない。

## 対象画面

- ダッシュボード: テナント、掲載、確認待ち、管理者の横断集計
- テナント管理: 組織、ownerアカウント、状態、掲載数の一覧と詳細
- 掲載管理: 宿泊・求人Listingの状態確認と公開停止
- 管理者管理: super_admin／operatorと有効状態の確認
- 運営アクティビティ: 重要な更新履歴の表示

テナント作成・編集フォーム、管理者招待、実際の削除、Rails API・DB接続、監査ログの正式設計は対象外とする。

## ファイル構成

- `prototype/admin.html`: 運営管理用シェル
- `prototype/admin.css`: 運営管理画面専用スタイル
- `prototype/admin.js`: 画面描画、検索・絞り込み、疑似状態更新
- `prototype/data/admin-workspace.json`: Admin、テナント、掲載、アクティビティのサンプル
- `prototype/README.md`: 起動URLと操作説明

## データ方針

`adminAccount` と `admin` を分離し、認証情報とロール・状態の境界を維持する。テナント側も `account`、`tenantMember`、`tenant` を分離した表示用集約とする。Listingは共通属性として `listingType`、`status`、`tenantId`を持つ。

編集結果はテナント画面とは別キーの `localStorage` に保存する。リセットで初期JSONへ戻す。

## 実装手順

1. Admin専用のサイドナビゲーションとログイン管理者表示を作る。
2. ダッシュボードへ集計、要確認項目、最近のアクティビティを表示する。
3. テナント一覧に検索・状態フィルターを追加し、詳細を表示する。
4. 掲載一覧に種別・状態フィルターと公開停止操作を追加する。
5. 管理者一覧とロール・状態を表示する。
6. READMEへAdminプロトタイプのURLを追加する。

## 検証方針

静的HTTPサーバーでAdminの初期表示、各画面遷移、フィルター、状態更新、リセットを確認する。今回はUIプロトタイプを優先し、自動テストは追加しない。

## トレードオフと今後

AdminによるListing更新は認可設計上可能だが、公開停止理由やテナント通知は未定義のため、プロトタイプでは確認ダイアログと状態更新だけに留める。正式実装前に監査履歴、通知、復旧手順を定義する。
